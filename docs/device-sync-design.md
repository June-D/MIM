## 1. 要解决的问题

换一台电脑登录同一账号，希望能看到**自己在别的设备上聊过的历史**。
现在的行为是：新设备只有一个空列表，因为历史只存在于各台设备的本地加密保险库。

这是产品最大的功能缺口，也是最容易做出安全事故的地方：
「把历史给另一台设备」在没有服务端明文的前提下，等于「让持有私钥的设备
把明文重新加密给一台新设备」。谁有权触发这件事，决定了这个功能是特性还是漏洞。

## 2. 现状盘点：服务端已就绪，客户端为零

服务端在 Phase 2 就为这件事留好了接口，协议与鉴权都在，缺的是客户端。

| 能力 | 位置 | 状态 |
|---|---|---|
| 请求同步（通知同账号其它设备） | `POST /message/sync/request` → WS `100022 {deviceId}` | ✅ 已实现 |
| 提交同步副本 | `POST /message/sync`（限流 60/分） | ✅ 已实现 |
| 副本归属校验 | `syncReplicas` → `requireOwnDevice`：目标设备必须属于本账号 | ✅ 已实现 |
| 副本重放/伪造防护 | 必须带 `syncSignature` + `syncOriginalFrom/To/Device`，缺一即拒 | ✅ 已实现 |
| 清除点对齐 | 副本落库前比对 `clearCursor`（含 `tag:` 维度），已清除的不再补发 | ✅ 已实现 |
| 撤回凭证继承 | 副本共用原消息的 `recall_token_hash` | ✅ 已实现 |
| 客户端：请求 / 转发 / 接收 | `MessagingBackend`、`AppStore`、`SecureBackend` | ❌ 完全没有 |
| 客户端：对原消息归属签名 | Rust 内核 | ❌ 没有签名导出（只有 `verifySignedPreKey` 这类验签） |

结论：**服务端不用改协议**，工作量集中在客户端与 Rust 内核。

## 3. 威胁模型

沿用 [`security.md`](security.md)：对手能读数据库、能改服务端响应，但没有设备私钥。
本功能新增的对手能力是：

- **A. 拿到账号密码 / JWT 的人**（例如撞库、设备被短暂控制）；
- **B. 能改服务端响应、诱导客户端把历史发给错误设备的人**；
- **C. 恶意服务端**：自己伪造一条「请把你的历史发给设备 X」的推送。

必须守住的不变量：

1. 转发的内容**只能**是转发设备本机能解密的明文（服务端永远拿不到明文）；
2. 只有**用户显式同意**过的那台设备能收到历史，默认不自动转发；
3. 服务端不能通过篡改响应让「本应发给我的设备」变成发给别人的设备——
   归属由转发设备用身份私钥签名，接收端用**已 pin 的设备公钥**验签；
4. 已清除的会话不会被同步「复活」（服务端已拦，客户端也要在落库前再挡一次）；
5. 同步只在本账号内发生，不改变「服务端不知道你和谁聊」的前提
   （它仍然知道「你的两台设备之间发生了同步」，这是可接受的元数据）。

## 4. 设备信任模型（核心决策）

### 选项

| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **A. 自动转发** | 收到 `100022` 就把最近 N 条发给请求方 | 体验最好 | **拿到 JWT 的人注册一台新设备即可拉走全部历史**，等于把 2FA 的保护面绕过 |
| **B. 显式批准 + 指纹核对**（推荐） | 源设备弹窗显示目标设备 id 与公钥指纹，用户确认后才转发；确认结果记入本机信任列表 | 攻击者拿到令牌也拿不到历史；可与「安全码」共用一套心智 | 需要另一台设备在线并有人点确认 |
| **C. 只做导出/导入文件** | 手动导出加密归档，另一台设备导入 | 最简单、最安全 | 不是「同步」，是搬家；用户预期不符 |

### 选择：B，并加两道硬限制

1. **目的设备必须「新注册」才需要确认**：在源设备的信任列表里已有记录的设备
   （指纹一致）后续同步不再弹窗，避免每次开机都打扰；
2. **单次同步上限**：最近 **50 条 / 最多 30 天**，且只补「本机留存了明文」的消息。
   不做全量搬迁——全量会让「设备被偷后拉走十年历史」的破坏面太大。

弹窗文案必须写清三件事：哪台设备在请求、它会拿到什么范围、拒绝后它会看到空列表。

### 自举（第一台设备）

账号的第一台设备没有可确认的对象，直接标记为「已批准」。
第二台设备首次登录时，服务端 `POST /device` 已经登记，此时：
- 若账号只有这一台设备 → 无需同步，直接空列表；
- 若还有其它设备 → 走上面的确认流程。

## 5. 端到端流程

```
新设备 B                          服务端                        旧设备 A
  │  POST /message/sync/request     │                              │
  ├────────────────────────────────▶│  WS 100022 {deviceId: B}     │
  │                                 ├─────────────────────────────▶│
  │                                 │                    弹窗：B 请求历史
  │                                 │                    用户点「同意」
  │                                 │                              │
  │                                 │   为 B 建立会话（X3DH + 预密钥）│
  │                                 │◀─────────────────────────────┤
  │                                 │   POST /message/sync          │
  │                                 │   （每条：sealed 密文 + 归属 + 签名）
  │                                 │                              │
  │  WS 100010（普通新消息推送）      │                              │
  │◀────────────────────────────────┤                              │
  │  GET /message/undelivered       │                              │
  ├────────────────────────────────▶│                              │
  │  解密 → 校验签名 → 恢复归属 → 入库                              │
```

### 5.1 转发端（设备 A）

1. 收到 `100022`，取出目标 `deviceId`；
2. 校验它确实属于本账号（服务端已保证，但客户端再查一次 `GET /device`）；
3. 查本机信任列表：指纹一致 → 直接转发；否则弹窗确认，确认后把`deviceId + 身份公钥指纹`记入信任列表；
4. 取「最近 50 条、30 天内、本机有明文」的消息，按会话分组；
5. 对每个目标设备：
   - 若已有棘轮会话 → 直接复用；否则拉取它的预密钥包、X3DH 建链（走现有 `composeFirstMessage`）；
   - 逐条 `composeSealed`，正文放进 **SyncEnvelope**：
     `{kind:"sync", clientMsgId, originalFrom, originalTo, originalDevice, clientTime, ciphertextRef}`；
   - 对 `clientMsgId|tag|originalFrom|originalTo|originalDevice|fingerprint` 用**本设备身份私钥**签名；
6. 批量 `POST /message/sync`（服务端逐条校验、已清除的跳过并回一条空壳）；
7. 结果里被跳过的条目直接丢弃，不重试。

> 关键点：转发的是**重新加密的密文**，不是把原密文转手。原密文用的是 A↔对端的棘轮密钥，
> B 解不开。这也是为什么必须有 A 在线参与，服务端无法独自完成同步。

### 5.2 接收端（设备 B）

1. 同步副本作为普通未投递消息到达（`to_user = 自己`、`target_device_id = B`、`sync_from_device = A`）；
2. 解密后拆 SyncEnvelope，得到原消息归属；
3. 用 A 的**已 pin 身份公钥**验签（首次见到 A 走 TOFU，与安全码同一套信任锚）；
   验签失败 → 丢弃并记一条本地告警，不猜测来源；
4. 二次清除校验：本机若已有清除点（`clearedBeforeId` / `updatedAt`）覆盖这条，丢弃；
5. 入库：用 `originalFrom/originalTo` 还原「谁说的」，副本自身的 `to_user` 不作为归属依据；
   本地缓存条目打 `syncedFrom = A` 标记，便于排查；
6. 媒体消息：只同步引用与密钥，**不搬运密文文件**。B 首次打开时按需下载；
   若已过服务端保留期，则显示「附件已过期」，与现有行为一致。

## 6. 数据结构

### Rust 内核新增（唯一改密码学的地方）

```rust
/// 用设备身份私钥签名（P-256 ECDSA / SHA-256），返回 base64url。
pub fn sign_with_identity(identity_private_b64: &str, payload: &[u8]) -> Vec<u8>;

/// 用对端身份公钥验签。
pub fn verify_with_identity(identity_public_b64: &str, payload: &[u8], sig: &[u8]) -> bool;
```

导出到 `MimCoreNative.signWithIdentity / verifyWithIdentity`，JNI 签名与现有
`verifySignedPreKey` 保持同样的入参风格（base64 字符串进出）。

### 同步信封（客户端 DTO，放在 `Protocol.kt`）

```kotlin
@Serializable
data class SyncEnvelopeDto(
    val v: Int = 1,
    val kind: String = "sync",      // 固定值，便于将来扩展
    val clientMsgId: String,
    val originalFrom: String,
    val originalTo: String,
    val originalDevice: String,
    val clientTime: Long,
    val message: CipherMessageDto,  // 内层密文（对该设备会话加密）
)
```

外层仍走现有 `CipherMessage` 结构，`alg = ratchet`，带 `syncSignature` 与
`syncOriginal*` 三个字段——服务端已按这套校验，不需要改。

### 客户端本地新增

| 文件 | 内容 |
|---|---|
| `trusted_devices.bin` | 已批准设备：`deviceId → 身份公钥指纹 + 批准时间`（加密落库） |
| `sync_state.bin` | 每台对端的同步游标（最近一次同步的 `epochMs`），避免重复搬运 |
| `plaintext_store.bin` | 自己发出消息的明文副本（`sent|peer|clientMsgId`），用于转发；只保留 30 天 |

> 第三条是必须的：棘轮不能解密自己发出的密文，A 要转发「自己说过的话」，
> 只能靠本机自己留一份明文。这也解释了为什么「换设备后旧历史找不回」——
> 那台设备没留，谁都补不了。

## 7. 失败与退化

| 情况 | 行为 |
|---|---|
| 源设备离线 | B 一直空列表；界面上说明「历史同步需要另一台设备在线确认」 |
| 用户拒绝 | B 收到拒绝信号（`100022` 的反向结果或超时），界面提示「另一台设备拒绝了本次同步」 |
| 源设备已清除该会话 | 服务端 `clearCursor` 已拦，B 也拿不到 |
| 源设备没有明文（更早的历史） | 不补；界面如实说「只同步本机留存的最近记录」 |
| 媒体已过保留期 | 同步引用与密钥，打开时提示「附件已过期」 |
| 验签失败 | 丢弃该条并本地告警；不降级为「信任服务端给的归属」 |
| 多台源设备同时转发 | 按 `clientMsgId` 幂等入库（服务端也有 `selectByClientMsgId` 去重） |

## 8. 明确不做

- 不做「服务端代存明文副本」——那会摧毁整个产品前提；
- 不做全量历史搬迁（只 50 条 / 30 天）；
- 不做后台静默同步（必须有一次用户确认）；
- 不改「服务端不知道你和谁聊」的性质：同步副本的 `to_user` 是自己，
  `conversation_tag` 沿用原标签，服务端仍然只看到标签。

## 10. 分期与工作量

**Phase A（建议先做，1~2 天）**
只补文本消息、最近 50 条 / 30 天、显式确认、信任列表。
交付标准：两台设备能同步最近对话，拒绝时对方拿不到任何东西。

**Phase B（+1 天）**
媒体引用与密钥同步（不搬密文）、同步游标、多源设备幂等。

**Phase C（可选）**
「导出/导入加密归档」作为离线兜底（方案 C），解决源设备已经不在的情况。

## 11. 待确认的问题

1. **确认弹窗放在哪台设备**：目前设计是源设备（A）弹窗。若 A 是无人值守的机器，
   同步就永远卡住——是否需要「B 端输入 A 端展示的 6 位确认码」双向确认？
2. **信任列表的撤销入口**：设备管理页已有「注销设备」，是否把「已批准历史同步」
   单独列出来可撤销？
3. **50 条 / 30 天是否够用**：产品上是否接受「换机后只能看到最近一小段」？
4. 同步副本是否要出现在对方的会话里——不会，但要不要在 B 端提示
   「以下 N 条来自另一台设备」？

以上四点确认后即可进入 Phase A。

## 12. 实现备注（2026-11 盘点时确认的硬约束）

写这块代码前先看这条，能省一次返工：

1. **DTO 缺字段**：客户端 `CipherMessageDto` / `CipherMessageOut` 目前没有
   `syncFromDevice`、`syncOriginalFrom/To/Device`、`syncSignature`。
   服务端 `POST /message/sync` 强制要求后四项，所以第一步是补 DTO（服务端不用改）。
2. **会话要按「自己」建**：同步副本的目标是**本账号的另一台设备**，不是联系人。
   因此 A→B 的棘轮会话应登记为 `peer = 自己的用户名`、`device = B 的设备 id`，
   与联系人会话共用同一套 `session_store`，靠 `device_id` 区分。
   不要试图复用与联系人的会话——那会把两套棘轮搅在一起。
3. **接收端要能认出「这是同步副本」**：`poll()` 目前只按 `from` 归属。
   同步副本的 `to_user` 是自己、发送方为空，只有 `sync_from_device`；
   需要先读 `syncFromDevice` 判断，再解信封里的 `originalFrom/originalTo` 还原归属，
   否则会显示成「我发给自己的消息」。
4. **自己发出的消息需要明文副本**：棘轮解不开自己的密文，转发「我说过的话」
   只能靠本机留存的明文（设计里的 `plaintext_store.bin`，30 天）。
   目前 `CachedMessage` 只存展示文本与载荷，够用，无需新存储——但要在
   `cache()` 里明确保留 `fromMe` 消息的 `text`（现在就是这么做的，注意别被清理逻辑删掉）。
5. **验证顺序建议**：先写一个双设备 e2e（同一账号两个 `SecureBackend` 实例，
   用临时保险库）把 `请求 → 组装 → 提交 → 拉取 → 验签 → 入库` 打通，
   再动 UI。UI 只是这层的壳，先做壳会让问题难以定位。

第 1 条（补 DTO）可以作为下一步的最小提交，独立可测。
